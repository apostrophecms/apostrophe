Adds `@apostrophecms/mcp`, an MCP server that lets an outside AI tool, such as Claude, ChatGPT or an IDE, work on the site's content as a connected user. It is off unless `enabled: true` is set. The outside tool brings its own model, so this module never calls Apostrophe's AI. It serves one route, `/api/v1/@apostrophecms/mcp`, for both current (2026-07-28) and 2025-era MCP clients. Its tools are the content tools the assistant uses, limited to what the connected user may read and change. It never lists or runs a tool that calls Apostrophe's own AI (`kind: 'agent'`), whatever its tags, so an outside tool can't spend the site's AI budget. It also offers `publish_document`, so the tool can publish what the connected user may publish. It's marked destructive, so MCP clients ask before running it, and the `publish: false` option leaves it out. Two tools are for the media library. `save_image_to_media` adds an image from base64 data, with a title and alt text, and returns its id for use in widgets. The image is published at once. On a site with several locales, it also takes `locale`. `get_image` returns an image's title, alt text, dimensions and file type, and a full link to each of the project's image sizes (the attachment module's `imageSizes`) with that size's dimensions, smallest first. It never returns the image's data. An image goes through the same intake as an upload, with the same allowed file types and SVG sanitizing, and a file that isn't an image is refused before it is stored. An image's size is limited by the `maxImageSize` option, in bytes. Unset, it's the `@apostrophecms/attachment` module's `maxSize` when that is a number of bytes, otherwise 10 MB (10,000,000 bytes). Sizes in messages are in decimal units, as Finder and the media library show them. Images arrive as base64 in JSON, and the JSON body limit is 16 MB, so a limit over about 12 MB also needs `bodyParser.json.limit` raised on `@apostrophecms/express`. Every edit to a document is saved as a draft, marked as made by AI, and recorded in the change log. The result of each change carries a request id, and the `get_changes` tool takes that id to report what changed. The connected user comes only from a bearer token in the `Authorization` header: an access token from `@apostrophecms/oauth`, which the MCP server turns on (so enabling MCP now requires the site's `baseUrl`), so the user approves each tool once on the site's approval page and can disconnect it under "Connected tools". A session cookie, an API key, or a token sent in the query string, the body or a cookie is ignored. A request without a valid token gets a 401 response that points the tool at the server's OAuth metadata, which is how MCP clients find where to ask for approval. For development only, `APOS_MCP_DEV_TOKEN=<token>:<username>` connects as that user, and keeps working when the OAuth server is turned off with `enabled: false`. It is ignored in production. The harness refuses an AI write to a document that was saved after the AI read it. Over MCP, each connection remembers what it read across tool calls, so an outside tool can't overwrite edits made after it read a document. A refused write now tells the AI who saved the document, for the assistant too, which still reads the document again before writing it. Over MCP, which has no confirmation step of its own, the AI is also told, when another user saved it, to say what they changed and to write only if the user asks; when it was the same user, in the admin UI or another of their chats or tools, it reads the document again and builds on that save. A door opts into this with `withDoor`'s `askBeforeOverwrite`. Each connection remembers its 100 most recently read or written documents; the `seenLimit` option changes that. A browser request whose `Origin` names another host is refused. The `allowedOrigins` option lists the hostnames allowed, and by default it is `baseUrl`'s hostname, or localhost when `baseUrl` is not set. MCP clients see the server under the site's `shortName`, and the `title` option sets the name they display instead.
