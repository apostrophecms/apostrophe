Security: the page and piece REST APIs now remove fields restricted by `viewPermission` from every document they return to a user who lacks that permission, not just from the requested documents themselves. This includes documents loaded through relationships (also nested and reverse relationships, and relationships inside widgets, array fields and object fields), the related pages embedded in page responses (`_ancestors` and `_children`), the home page response and page `autocomplete` results. The same now applies to the documents returned after a write: `POST`, `PUT` and `PATCH` (including archiving, restoring and moving pages), publish, unpublish, revert, localize and share, as well as `GET /api/v1/@apostrophecms/doc/:_id` and a single document version. Saving a document without those fields in the request body still leaves their stored values untouched, as before. Each document is filtered according to its own type's schema. A `project` query parameter can also no longer exclude `type` or `metaType`, which could previously be used to keep a page's restricted fields in the response. The reported problems with `GET /api/v1/@apostrophecms/page/:_id`, which in 4.32.2 and earlier ignored type-level `viewRole` and did not remove `viewPermission` fields, were already corrected in 4.33.0 and are now covered by additional tests. Enforcing `viewRole` on that route was always the intended behavior, and the earlier behavior was a bug that should not have been relied upon. This only affects sites that use `viewPermission`. Anonymous visitors were affected only where a `publicApiProjection` includes a relationship to documents of a type with such fields (CWE-200, CWE-863, GHSA-vh56-5m88-39rq).

Thanks to [harshavardhan98899-lab](https://github.com/harshavardhan98899-lab) for reporting the vulnerability.
